================================================================================
 GAUSSIAN-SMOOTHED DPS CURVE - ADVANCED IDEAS (not implemented yet)
================================================================================
 Companion to dps_curve.py + ui/tabs/results.py. The shipped version is the
 MINIMAL chart: one filled smoothed curve + the dashed overall-DPS line. No hit
 rug and no user-facing sliders: sigma 0.70 s / truncation 2.20 s are pinned as
 DEFAULT_SIGMA / DEFAULT_TRUNCATION in dps_curve.py, and the sliders are kept
 commented in _render_dps_chart() for re-tuning. Everything below was parked.

 Environment: Streamlit 1.66.1, Plotly 7.1.0, numpy 2.5.4, pandas 3.1.0.
 requirements.txt has streamlit / pandas / numpy / plotly. NO scipy - keep it that
 way (the truncated Gaussian is 3 numpy lines).

--------------------------------------------------------------------------------
 1. MEASURED DATA (why the defaults are what they are)
--------------------------------------------------------------------------------
 Flagship preset "Mizuki Sac Frag Pull out 6x rotations", presets.DEFAULT_PARTY:

   duration            118.212 s
   events              665  (587 damaging HITs, rest are audit rows)
   total damage        5,594,390
   overall DPS          47,330   (= total / duration)
   hit gaps (damaging)  median 0.098 | p90 0.621 | p99 1.141 | max 1.230 s
   189 of 586 consecutive pairs have gap == 0.000 s  (multi-hit procs)
   225 pairs are < 0.02 s
   elements present    Anemo, Cryo, Physical
   Anastasya variant   633 hits, median 0.055, p99 1.22, max 1.77 s

 Area under the curve vs total damage (sigma X, truncation 1.5 s, dt 0.05 s).
 These were measured while the truncation was still 1.5 s; the shipped chart now
 uses 2.20 s (see the note below the table):

   sigma 0.10 -> peak 324,844 DMG/s   area 99.60 % of total
   sigma 0.15 -> peak 216,571         99.55 %
   sigma 0.20 -> peak 162,943         99.50 %
   sigma 0.30 -> peak 124,399         99.45 %
   sigma 0.50 -> peak  90,419         99.35 %

 The shipped chart uses sigma 0.70 s and truncation 2.20 s (auto_params() returns
 2.205 s = TRUNCATION_SIGMAS 3.15 x 0.70). Measured on the flagship preset at those
 settings: peak 75,360 DMG/s (= 1.59x the 47,325 overall DPS) and curve area 99.24 %
 of the total. At sigma 0.20 the auto truncation gives 1.5 s and the peak is
 170,973 DMG/s, i.e. ~3.6x the overall DPS.

 The shipped kernel is normalised over its full window and NOT renormalised when
 the trial boundary clips it, so the chart reports ~99.2 % of the total and never
 invents damage at the edges (see problem 1). The numbers above use the raw
 continuous normalisation, which is the same shape.

 Rules of thumb:
   * truncation >= max_gap / 2  -> neighbouring windows overlap (0.615 s / 0.885 s)
   * sigma is what decides smoothness, truncation only decides where the bell stops
   * sigma >= 4 * dt            -> the bell is never thinner than 4 samples
   * peak ~ 1 / (sigma * sqrt(2*pi)) per hit, so peak / mean DPS grows as sigma
     shrinks (6.9x at sigma 0.1, 3.4x at 0.2, 1.9x at 0.5)

 2. DISPLAY IDEAS, IN ORDER OF VALUE / COST
--------------------------------------------------------------------------------
 (a) CLICK-TO-INSPECT  [medium cost, biggest payoff]
     st.plotly_chart(fig, on_select="rerun", selection_mode="points",
                     key=f"dps_click_{real_idx}")
     then read event.selection.points[0]["x"] and render the audit rows within
     +/- truncation of that time. Reuse the code the tab already has:
       df = build_timeline_dataframe(hits_near, party=sim_party)
       st.dataframe(style_timeline_dataframe(view),
                    column_config={k: v for k, v in AUDIT_COLUMN_CONFIG.items()
                                   if k in view.columns},
                    placeholder="-")
     This turns "why is there a spike at 12.3 s" into a one-click answer.
     Caveats: the curve trace is 2,400 points, so a click usually snaps to the
     nearest grid sample (+/- dt/2). Filter to the "Hits" trace if the point
     includes "trace_name", and keep the audit row keys unique per entry.

 (b) SPLIT BY CHARACTER (stacked areas)  [medium cost, high payoff]
     dps_curve.gaussian_dps is linear, so one curve per owner plus one for
     "Reaction" sums EXACTLY to the team curve. Draw them with
     go.Scatter(..., stackgroup="one") under a checkbox
     "Split by character (excl. reactions)", with reactions as their own bucket
     (get_analytics_summary already excludes them from owner_damage_share).
     Colour source: ui/style.py OWNER_BG is already a per-character palette, but
     it is tuned for table row tints (very dark). Add a sibling CHART_OWNER_BG
     with mid-tone equivalents instead of reusing OWNER_BG directly.
     Compute cost: 4-5 x one curve, still < 30 ms. Cache the per-owner series in
     st.session_state if the tab feels sluggish with many history entries.

 (c) SHARE OF DPS / NORMALISED VIEW  [low cost]
     Divide the curve by overall_dps and label the y-axis "x overall DPS". Makes
     two different trials (different gear) shape-comparable: a 3x spike means the
     same thing in both. Add as a st.segmented_control(["DMG/s", "x overall"]).

 (d) LOG SCALE  [one line]
     tick "Log y" -> fig.update_yaxes(type="log"). Without it, one 300k crit spike
     flattens the entire 0-20k baseline. With it, quiet phases become readable.

 (e) ELEMENT-COLOURED CURVE  [low cost, cosmetic]
     Instead of colouring only the rug dots, draw one curve per element
     (Anemo / Cryo / Physical here) with the palette already used by the element
     pie charts, so the chart and the pie agree visually.

 (f) ROTATION LINES / PHASE BANDS  [medium cost]
     The audit rows carry the active character and the field-sequence windows.
     Drawing vrect bands per character field (or per rotation rep) behind the
     curve explains "burst windows" at a glance, and aligns with the strips in
     ui/editor/strips.py if the same palette is used. The strip itself is a custom
     iframe component, so pixel-perfect alignment is NOT practical - draw the
     bands in Plotly instead.

 (g) CSV EXPORT OF THE CURVE  [low cost]
     st.download_button("Download curve CSV", pd.DataFrame({"t": grid, "dps": curve})
                        .to_csv(index=False), file_name="dps_curve.csv").
     Useful for external sheet comparisons; regenerate with the same sigma /
     truncation the user is looking at so the file matches the chart.

 (h) SMALL-MULTIPLES: one row per history entry  [high cost, questionable]
     With 5+ saved runs, a 2-row grid of mini curves (no axis labels, shared
     y-range) makes A/B comparisons instant. Requires computing every entry's
     curve on each rerun (already cheap) but the tab gets crowded; a
     st.tabs(["Chart", "Compare"]) split is cleaner if this is ever wanted.

 (i) HOVER RICHNESS  [low cost]
     Add customdata = hit damage and hovertemplate with the ability name for the
     rug trace, e.g. "%{x:.2f}s · %{customdata[0]} · %{customdata[1]:,.0f} dmg".
     Keep "x unified" so the curve value and the hit value appear together.

 3. PREDICTED PROBLEMS (and the fix each one needs)
--------------------------------------------------------------------------------
 1. Kernel normalisation. Bells cut at +/- truncation hold only
    erf(truncation / (sigma*sqrt(2))) of their area (2 sigma -> 95.4 %), so the
    SAMPLED kernel must be normalised to sum 1. Do NOT also renormalise a window
    that the trial boundary clipped: it props up half a bell and turns the trial's
    last hit into a fake spike. Measured on the flagship preset, the curve maximum
    moved from the real burst to t = 118.2 s (220,975 vs 162,943 DMG/s). The
    shipped version leaves clipped tails clipped and reports the resulting 99.4 %.

 2. Simultaneous hits. 189/586 gaps are exactly 0 (Mizuki multi-hit procs). Never
    merge hits by timestamp and never build a {time: damage} dict - it would
    silently drop every proc that shares a timestamp with another.

 3. dt vs sigma. With dt > sigma/4 the curve is an aliased triangle; with a hit
    landing on one sample the peak becomes damage/dt (20x at dt=0.05). Guard:
    sigma >= 4*dt, enforced inside gaussian_dps, and the UI derives dt = sigma/4.

 4. Peak vs average confusion. "Why does the graph say 300k when my DPS is 47k?"
    The dashed average line + the caption ("smoothed instantaneous rate") is the
    cheapest answer. The normalised view (c) is the strongest one.

 5. Truncation below max_gap/2. The curve drops to exactly 0 between rotations
    and looks like missing data. The shipped 2.20 s window clears the 0.615 s
    requirement by 3.6x; if you re-enable the sliders, keep truncation above
    max_gap/2 (the commented diagnostics print the required minimum).

 6. Slider keys. results.py renders every history entry in one rerun, so widget
    keys MUST include real_idx (they do: dps_sigma_{idx} / dps_trunc_{idx}).
    Renaming a run calls st.rerun() - the curve is rebuilt, ~5 ms, fine.

 7. Old history entries without timeline_events. Handled with a caption fallback;
    never index entry["timeline_events"] directly (it was a KeyError risk in the
    old code path too).

 8. Payload size. dt=0.05 gives ~2,370 points for a 118 s trial. A 10-minute
    custom trial would be 12,000 points at the same dt; unified hover starts to
    feel heavy around 40-50k points. auto_params already clamps dt, but a real
    long-trial guard would be dt = max(dt, duration / 4000).

 9. Removing analytics["dps_timeline"]. Any external script that reads the
    analytics dict from a saved history entry loses that key. Nothing in this
    repo does (verified by grep). If a build JSON ever needs it, recompute from
    the hit rows instead of storing a second copy.

10. Plotly quirks: line_shape="spline" overshoots and can dip below 0 between
    spikes - keep the default linear shape. fill="tozeroy" with a linear trace is
    exact. Keep rangemode="tozero" so small fluctuations do not look like
    negative DPS.

--------------------------------------------------------------------------------
 4. SMOKE TEST (implemented as check 2r: _run_dps_curve_check)
--------------------------------------------------------------------------------
 The shipped block in smoke_test.run() pins:

   * one isolated hit peaks at damage / (sigma * sqrt(2*pi)) (exact closed form),
   * its area equals its damage when the window is fully inside the trial,
   * a hit at t=0 keeps its peak but only ~50 % of its area (clipped, not inflated),
   * a preset trial: 99.0 % <= visible area / total_damage <= 100.0 %,
   * the curve is finite and never negative,
   * auto truncation >= max hit gap / 2 (windows overlap, no dead zone).

 Values measured by the run: 587 hits, area 99.56 % of 5,594,390, peak 170,973
 DMG/s at sigma 0.20, max hit gap 1.23 s (auto truncation 1.23 s).

 Kept as a tolerance rather than an exact number because the gap and the peak are
 gear dependent: pin "max gap > 1.0 s" and the 99-100 % band, not 1.230 / 162,943.

--------------------------------------------------------------------------------
 5. OPEN DESIGN QUESTIONS
--------------------------------------------------------------------------------
 * Should the curve use average_damage (as now) or offer a non-crit/crit view?
   Average matches the Total Damage card; a crit view would need events to carry
   a chosen roll, which the engine does not store per event.
 * Does "per-second" still have value for anything (CSV export, external sheet)?
   If yes, keep a tiny np.add.at impulse array in dps_curve.py instead of
   restoring the engine-side binning loop.
 * Should sigma persist across history entries (one global slider) or per entry
   (current)? Per entry is safer: comparing runs is exactly when you want the
   same sigma, but a global control can come later as a st.popover "chart
   defaults" that seeds the per-entry sliders.
